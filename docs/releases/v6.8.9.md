## 2026-10-25 — App-wide scrollbar consistency (shadcn) — REVERTED, see "Outcome" at the end

> **Status: the `ScrollArea`-in-dropdown approach described below was reverted.** It broke scrolling outright — dropdown options could not be scrolled at all across the app. Read the "Outcome / what to do instead" section at the end before retrying any of this. The notes below are kept because the root-cause analysis is still valid and worth not re-deriving.

- The sidebar's collapsed group flyout (e.g. "CRM & Sales") rendered its popup menu with a plain native browser scrollbar instead of the slim, theme-matched shadcn `ScrollArea` thumb used in the inbox list. Root cause: `DropdownMenuContent` (`src/components/ui/dropdown-menu.tsx`) only applied `overflow-y-auto` + a CSS `scrollbar-thin` utility, which depends on the browser actually honoring custom `::-webkit-scrollbar` styling — unreliable across embedded/webview renderers. It now wraps its children in the shared `ScrollArea`/`ScrollBar` primitives, matching the inbox conversation list's recipe: 6px thumb, `bg-muted-foreground/30` → `/55` on hover → `primary/65` on active, hidden until hover/focus. Since every dropdown menu in the app (`SidebarGroupFlyout`, header menus, row action menus, etc.) renders through this one shared component, the fix applies app-wide automatically.
- Applied the same `ScrollArea`-wrapped fix to `ContextMenuContent` (`src/components/ui/context-menu.tsx`) for the same reason and the same visual recipe.
- The Plugin Marketplace category filter rail (`src/routes/_authenticated/marketplace.plugins.index.tsx`) had a thick native horizontal scrollbar. Converted it to the shared `ScrollArea` in horizontal mode, matching the pattern already established by the header notification filters (`notification-center.tsx`): a 5px hover-reveal thumb using the same muted-foreground color recipe.
- `SelectContent` (`src/components/ui/select.tsx`) and `CommandList` (`src/components/ui/command.tsx`) scroll through Radix/cmdk's own internal viewport, which manages keyboard scroll-into-view and can't be safely re-wrapped in a second `ScrollArea` without breaking that behavior. Added the `scrollbar-thin` utility class to both so they at least opt into the app's matching 6px/muted-foreground native-scrollbar recipe (`src/styles.css`) rather than relying on inheritance alone.
- Scope note: a broad sweep found ~85 other call sites using plain `overflow-x-auto`/`overflow-y-auto` (tables, kanban boards, tab strips, etc.). These already inherit the app's global thin/colored native-scrollbar CSS (`src/styles.css`, the `*` rule under "Refined scrollbars (shadcn-inspired)") and were left on the native recipe rather than rewritten speculatively.

### Follow-up — the first pass didn't actually fix the flyout/Settings menu; found the real bug

The user came back with 4 more screenshots (Settings flyout, notification panel, inbox channel dropdown, inbox view dropdown) still showing thick native scrollbars after the first fix above. Root-caused two separate bugs:

1. **`cn()`/`tailwind-merge` silently defeated the wrap.** `DropdownMenuContent` callers that passed their own `overflow-y-auto`/`max-h-*` in `className` (`inbox-view-menu.tsx`, `feature-manager.tsx`) had that merged in via `cn(...)`, and tailwind-merge let the caller's `overflow-y-auto` win over the base `overflow-hidden`, re-enabling native scroll on the outer element and making the inner `ScrollArea` wrapper a no-op. Fixed by stripping the now-redundant `overflow-y-auto` from both call sites — the shared component handles scrolling internally now.
2. **Many menus scroll an inner `<div>`, not the outer `DropdownMenuContent`.** Several menus keep a fixed header (e.g. a search box) above a separately-scrollable items list, implemented as their own inner `max-h-* overflow-y-auto` div — wrapping the _entire_ `DropdownMenuContent` in one outer `ScrollArea` never touches that inner div, which is what was actually rendering the visible scrollbar. Converted each inner div to its own `ScrollArea` (same recipe, and the same `className="max-h-N"` pattern already used elsewhere in this codebase, e.g. `label-manager.tsx`):
   - `conversation-list.tsx`: the channel/account picker's results list (`max-h-80`), its per-channel account sub-list (`DropdownMenuSubContent`, `max-h-[60vh]`), and the connection-status sync-history list (`max-h-32`).
   - `notification-center.tsx`: the main notification `<ul>` (`max-h-[420px]`) — this one hadn't been touched in the original "Main header notifications" work at all; only the horizontal section-filter strip had a `ScrollArea`.

Also hardened `DropdownMenuContent`/`ContextMenuContent` themselves: switched from `className="h-full max-h-[inherit]"` on the nested `ScrollArea` (relies on `max-height: inherit` resolving against an `auto`-height parent, which browsers don't always treat as a definite size for percentage children) to the proven `flex flex-col` + `ScrollArea className="min-h-0 flex-1"` pattern already used by the inbox conversation list — flex sizing doesn't have that resolution gotcha.

### Outcome / what to do instead

The user reported that after the above, **scrolling stopped working entirely** — dropdown options would not scroll at all anywhere in the app. Everything that wrapped menu content in a `ScrollArea` was reverted:

- `dropdown-menu.tsx` and `inbox-view-menu.tsx` are back to their committed state (byte-identical to HEAD).
- `context-menu.tsx`, `conversation-list.tsx` (channel picker list, channel sub-menu, sync-history list), `notification-center.tsx` (notification `<ul>`) and `feature-manager.tsx` are back to native `overflow-y-auto` scrolling.

**Lesson for the next attempt:** a Radix menu's `Content` is not a plain box you can nest a scroll container inside. Radix owns focus management and scroll-into-view for keyboard navigation on that element, and the menu's height is driven by its own collision/available-height measurement — putting a `ScrollArea` (which inserts its own viewport div between `Content` and the items) in the middle breaks the scroll chain. The two surviving, working examples of a custom scrollbar in a popup (the inbox conversation list, the notification filter strip) both put the `ScrollArea` around _non-menu-item_ content, which is why they work.

What is still in place after the revert (CSS-only, no behavior change, verified safe):

- The Plugin Marketplace category rail (`marketplace.plugins.index.tsx`) horizontal `ScrollArea` — this one is _not_ menu content, mirrors the already-working notification filter strip, and was left in.

**If the thick-scrollbar look needs fixing again, do it in CSS, not by restructuring menus.** The global recipe already lives in `src/styles.css` under "Refined scrollbars (shadcn-inspired)".

### The actual root cause and the real app-wide fix (`src/styles.css`)

The reason the shadcn recipe never showed up: the global rule set `scrollbar-width: thin` and `scrollbar-color` on `*`, **and since Chromium 121 either of those standard properties suppresses every `::-webkit-scrollbar` rule on the same element.** So the 6px thumb recipe underneath it was dead code in Chrome/Edge — the browser fell back to its own native "thin" bar, which on Windows is thicker, keeps the native grey look, and keeps the stepper arrows visible at each end of the track (clearly visible in the horizontal-rail screenshot). The `scrollbar-thin` utility had the same self-defeating pair.

Fixed by splitting the two engines with `@supports selector(::-webkit-scrollbar)`:

- Firefox (and anything without the pseudo-element) keeps `scrollbar-width: thin` + `scrollbar-color`.
- Chromium/WebKit releases both back to `auto` _inside_ the `@supports` block, which hands control to the pseudo-elements, then applies the real recipe: 6px track, `muted-foreground/30` thumb → `/55` hover → `primary/65` active, pill radius, transparent track/corner, and `::-webkit-scrollbar-button { display: none }` to drop the native arrows.

This is the app-wide enhancement: it is one shared rule, so **every** scrollbar in the app picks it up — dropdowns, menus, tables, panels, kanban columns, tab strips, vertical and horizontal alike — with zero component restructuring and therefore none of the breakage the `ScrollArea` approach caused. The shadcn `ScrollArea` component stays the recipe for the places that need an overlay-style custom bar and are _not_ Radix menu content (inbox conversation list, notification filter strip, marketplace category rail, and the ~55 other files already using it); the two layers now render the same 6px muted-foreground thumb, so they match.

Verified by compiling `src/styles.css` through the project's own Tailwind v4 (`tailwindcss.compile`): the output contains both `@supports selector(::-webkit-scrollbar)` blocks with `scrollbar-width: auto` and the full thumb/button recipe, and the `scrollbar-thin` utility emits once with no conflicting duplicate.

### Hover-reveal with fade, app-wide (2 shared files)

Final behavior pass, again done in shared code rather than per-component so it covers the whole app at once:

- `src/styles.css` — the thumb is now `transparent` at rest and fades in over 200ms when the scrolling region is hovered or focused (`*:hover::-webkit-scrollbar-thumb`, `*:focus-within::-webkit-scrollbar-thumb`, and the `scrollbar-color` equivalent for Firefox). Leaving the region fades it back out. Touch devices (`@media (hover: none)`) keep the thumb permanently visible since there is no hover, and `prefers-reduced-motion: reduce` drops the transition.
- `src/components/ui/scroll-area.tsx` — the shared `ScrollBar` now fades via `data-[state=hidden]:opacity-0` plus a 200ms opacity/color transition, so the shadcn component matches the native bars' timing. Deliberately no `data-[state=visible]:opacity-100`: that variant would out-specify the custom `opacity-0 group-hover:…` classes that call sites like the inbox conversation list (`type="always"`) pass in, and would have pinned their bars permanently visible.

Net effect: every scrollbar in the app — native or shadcn `ScrollArea`, vertical or horizontal — is a 6px muted-foreground pill, invisible at rest, fading in on hover/focus, darkening on thumb hover, and turning `primary/65` while dragged.

The demo write-guard (`src/lib/demo/admin-write-guard.server.ts`) blocks every write to business tables (only `sessions`, `login_history`, `account_lockouts` are exempt) and every RPC not in its small allow-list. This single misconfiguration causes:

- **#1 WhatsApp campaigns stuck in "Queued".** `enqueueCampaign` (runs on the user's JWT) correctly inserts recipients=`queued`, dispatch rows=`pending`, campaign=`running`. The pg_cron job then POSTs to `/api/public/hooks/campaign-dispatch`, which calls `claim_campaign_dispatch_batch` through the **demo-guarded** admin client → blocked → HTTP 500 → the WhatsApp Cloud API send (`delivery.server.ts`) is never reached and recipients never move off `queued`. **Live evidence: 564 HTTP 500s in the last 2 hours** in `net._http_response`, bodies = `Demo mode: call on "rpc/claim_campaign_dispatch_batch" is disabled`. The same guard is also failing `wf_queue_lease`, `scheduled_messages`, and `sync_jobs` crons.
- **#2 Messenger/Instagram messages not auto-appearing (current).** Both webhook handlers write inbound messages through the **same** demo-guarded admin client (`inbox-bridge.server.ts:31`, `instagram/webhook.server.ts:222`), so in demo mode the `conversations`/`messages` inserts are blocked. **Proof it works in production mode:** on 2026-10-06/07 (when the host was not in demo mode) real IG/Messenger DMs _did_ ingest — workspace `f32a2afc…` has 2 Instagram conversations / 6 messages and 2 Messenger / 22 messages from those dates. **The webhook code and ingestion logic are NOT broken** — the earlier hypotheses (http/https mismatch, missing Instagram branch, App Secret, ig_user_id mismatch) were ruled out by the data: the connected IG account `17841458113246993` (`mrh_hasan_12`) matches the `recipient.id` Meta sends, and its messages landed fine in production mode.

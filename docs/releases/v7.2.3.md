## Gmail inbox channel

Added Gmail as a 4th inbox-channel provider (alongside Resend/SMTP/Lovable), so a workspace can
connect a real Gmail mailbox via OAuth and have inbound mail land in the omnichannel Inbox, with
replies sent through the connected Gmail account.

**Scope decisions (made explicitly, not silently):**
- Reused the existing "Google Workspace" integration's OAuth client credentials
  (`GOOGLE_WORKSPACE_CLIENT_ID/SECRET` / `google_oauth_settings`) with a narrower, dedicated scope
  set for this channel — `userinfo.email`, `gmail.readonly`, `gmail.send` only (no Drive, Calendar,
  or Contacts). No new Google Cloud OAuth client was needed.
- Gmail is a new `email_accounts.provider` value, not a new table — it reuses the inbox/contact/
  conversation plumbing the Resend/SMTP email channel already has.
- Inbound delivery is **polling** (pg_cron every 3 minutes, via the existing `_wa_cron_post` →
  `/api/public/hooks/gmail-sync` pattern), using Gmail's `users.history.list` incrementally — not
  Google Cloud Pub/Sub push. Pub/Sub needs manual GCP Console setup (topic, subscription, granting
  `gmail-api-push@system.gserviceaccount.com`) that can't be done or verified from a coding session;
  it's a documented future upgrade, not built now.
- Connecting/disconnecting Gmail is workspace owner/admin-only, matching the existing `email_accounts`
  RLS policy.
- Secrets use the same crypto helper as the sibling `email_accounts` columns
  (`encryptToken`/`decryptToken`), so the table has one consistent secret-handling convention.

## Inbox readability and contact detail (follow-ups to the Gmail channel)

Three fixes found while testing the live Gmail channel:

1. **Quoted thread stripped from email replies** — `src/lib/email/quoted-text.ts` (new) splits a
   mail body into the new reply and the quoted thread below it, matching `On ... wrote:`, `>` runs,
   `-----Original Message-----`, and Outlook `From:/Sent:/To:` blocks. Gmail (unlike Postmark and
   Mailgun) ships no pre-stripped reply, so a two-word answer was arriving buried under the whole
   thread. Applied in three places: the stored `body` keeps only the reply (the quote is preserved
   in `metadata.quoted_text`), the chatbot is fed only the reply, and the message bubble renders the
   reply with a "Show quoted text" toggle. The UI splits at render, so messages already stored are
   readable too without a backfill.
2. **Sender display names adopted** — `resolveContact` only ever set a contact's name at creation,
   so a contact first seen without a display name kept its email address as its name forever.
   `adoptSenderName` now upgrades a placeholder name (empty, or equal to the address) when a real
   one arrives, and never overwrites a name a human has set.
3. **Contact location, with no paid service** — `src/lib/geo/country.ts` (new) resolves a country
   offline from three free signals, preferred in order: a phone's dial code, a browser locale's
   region subtag (`Intl.Locale`), and an IANA timezone. Country names come from `Intl.DisplayNames`
   and flags from Unicode regional indicators, so there is no name table and no API call. Shown as a
   "Location" row in the conversation hover card, marked "(approx.)" when it came from a locale or
   timezone rather than a phone. Note: live chat's `country`/`city` columns exist but are never
   populated (0 of 17 visitors), and Gmail strips the sender IP from `Received` headers, so IP-based
   geolocation was not a usable free option for email.

Verified: 50/50 unit tests pass (20 new across quoted-text and country resolution), ESLint clean on
every touched file, full `tsc --noEmit` clean. The country resolver was checked against the real
contact rows in the workspace — `880…` → 🇧🇩, `91…` → 🇮🇳, `234…` → 🇳🇬, `1470…` → 🇺🇸. A unit test
caught a real bug during this work: a 2-digit string matched the `+1` prefix and flew a US flag, so
the resolver now requires at least 7 digits before guessing.

## Duplicated inbound messages (fixed)

A customer's message was landing in the Inbox several times over — one photo arrived eight times,
and the chatbot answered it eight times. Two defects compounded:

1. **The idempotency guard disabled itself.** Every channel read its "have I seen this message id?"
   row with PostgREST's `.maybeSingle()`, which *errors* rather than returning data once more than
   one row matches. The error was discarded and `data` was `null`, so the guard read "not seen".
   That means the first lost race permanently broke de-duplication for that message id — each
   redelivery added another copy, which made the next read fail harder. Replaced with `.limit(1)`
   across all nine ingest paths (WhatsApp Cloud + QR, Telegram, Messenger webhook + sync, Instagram,
   Email, Gmail, social inbox).
2. **The guard was a check-then-insert, with a media download in between.** `processInboundMessage`
   fetches and caches the message's media *after* the duplicate check and *before* the insert, so
   the response stayed open long enough for Meta to re-deliver on its retry backoff — observed at
   1.5s, 19s, 22s, 33s, 52s and 6min for the same `wamid`. Nothing in application code can close
   that window, so the guarantee moved into the database:
   `20261101183000_messages_external_id_unique.sql` adds a unique index on
   `(workspace_id, external_message_id) where external_message_id is not null`, after folding
   existing duplicates into their earliest copy (replies are re-pointed at the survivor first).
   `processInboundMessage` now treats a `23505` on insert as "another delivery won" and returns,
   which also stops the duplicate chatbot reply.

Verified: the live database showed 9 duplicate groups / 24 extra rows, all inbound `whatsapp_cloud`,
all within a single conversation each — and zero cross-direction or cross-provider collisions, so
the unique index is safe. ESLint and `tsc` clean on every touched file.

**Needs the user:** applying this migration was blocked by the session's production-deploy guard, so
`supabase db push` still has to be run. Until it is, only defect 1 is fixed (which alone stops the
runaway 8-copy case; the rare sub-second race can still produce a single extra copy). Note also that
the duplicate *bot replies* were really delivered to the customer over WhatsApp, so they are left in
the thread rather than deleted — removing them would misrepresent what was actually sent.

## Destructive menu icons were grey

Every destructive menu item ("Delete", "Sign out", "Move to trash", …) renders its label with
`text-destructive`, but the icon beside it stayed muted grey, so the row read half-destructive.
The cause was in `src/styles.css`: the shared `menu-item-state` utility hard-sets

One central change covers every menu in the app (DropdownMenu, ContextMenu, Menubar, Select,
Command), since they all route through `menuItemClass()` → `menu-item-state`. No component files
were touched.

Verified: `node scripts/check-menu-item-tokens.mjs` passes, and the rule compiles into the
utilities layer as `.menu-item-state.text-destructive svg.lucide` (read back from the running dev
server's transformed `styles.css`), which outranks the muted default on specificity.

## WhatsApp QR login could not work at all

Asked to check whether QR login works. It did not, and the reason was one file.

`src/lib/messaging/qr-sessions.server.ts` carried its own `callWorker` that sent
`Authorization: Bearer <token>` and nothing else. The worker's `authenticate` middleware also
requires `X-WACRM-Timestamp` and `X-WACRM-Signature`, so **every QR operation the UI performs** —
start session, poll for the QR, revoke, reconnect, delete, revoke-all — answered **401**. The one
exception is `/health`, the only unauthenticated route, which kept reporting the worker as
reachable. That is why the worker looked fine and no QR ever appeared.

A correct signed client already existed in `qr-worker.server.ts` (used only by the auto-reply
path). The duplicate is gone; `qr-sessions.server.ts` now re-exports the signed one, and the two
POST call sites pass an object instead of a pre-stringified body (the signed client stringifies it
itself, and the signature must be over exactly what is sent).

**Reproduced and verified against a real worker** running locally against WhatsApp:

| Probe | Result |
| --- | --- |
| No credentials | `401 Unauthorized` |
| Bearer token only — *what the app used to send* | `401 Timestamp outside allowed window` |
| Bearer token + HMAC signature | `200` |
| `POST /sessions` | `200 {"worker_session_id":…}` |
| `GET /sessions/:id/qr` | real QR string (237 chars) after 4s, `status: awaiting_scan` |

### Three more worker defects fixed

- **A dropped connection never came back.** On a transient close the handler set
  `status = 'connecting'` and scheduled `startSession()` — but that function returns early unless
  the status is `disconnected` or `error`, and `connecting` is neither. The retry swallowed itself,
  so any network blip killed the session until someone restarted the worker by hand. The retry now
  passes an explicit `{ reconnect: true }` and backs off 3s → 10s → 30s → 60s → 2 min.
- **A restart left every number offline.** Sessions live in memory; the credentials on disk were
  never re-opened, so a deploy or crash silently disconnected everyone until someone pressed
  reconnect, losing inbound messages in the window. `restoreSessions()` now runs on boot. Because
  Baileys does not record which tenant a credential folder belongs to, the worker writes a small
  `wacrm-session.json` beside it. Verified: a folder with credentials is restored, a half-finished
  scan without `creds.json` is skipped with a warning, and a non-UUID folder is ignored.
- **Reconnects leaked sockets and lost idempotency.** Each restart built a fresh entry, discarding
  the `client_message_id` dedupe map (so a retried send could deliver twice) and leaving the old
  socket's listeners attached to the same entry (so events could fire twice). The entry is now
  reused and the previous socket is detached before being replaced.

Documentation: fixed the README's link to a contract file that does not exist (it is a section of
the docs site), and added what now happens automatically on restart and disconnect, plus a
troubleshooting table whose first row is exactly the failure above — health green, no QR.

**Known limitation, not fixed:** inbound media still reaches the app as `media_url: null`, so a
photo or document from a QR-connected number arrives as a message with a type and no file. Text,
receipts, replies and outbound media work. Fixing it needs the worker to download and hold the
file and the app to fetch it into storage — a feature, not a one-line repair, so it is left for a
decision rather than slipped in.

## Deleting an organization or an account did not stick

Reported as "it looks deleted, then it rolls back — the user and the organization still work."
Two unrelated defects, both confirmed against the live database.

### "Delete account" deleted nothing

`useDeleteAccount` in `src/hooks/use-profile.ts` only set the profile's `display_name` to
"Deleted user", nulled `bio` / `phone` / `full_name`, and signed out — while the UI reported
"Account deleted". The auth user, the organization, the workspaces and every owned row survived,
and the person could sign straight back in with the same password. The code said as much in a
comment: "Soft delete … Hard delete of auth user requires admin".

Replaced with a real server-side deletion, `deleteMyAccount` in
`src/lib/profile/account.functions.ts`: it re-checks the typed confirmation server-side, refuses
when the caller is the last super administrator (deleting them would leave the installation with
no way into the platform surfaces, and the first-run wizard will not mint another once an admin has
existed), runs `prepare_platform_user_deletion` to hand off owned tenants, then
`auth.admin.deleteUser`. The client signs out locally afterwards.

### Deleting an organization recreated it immediately

The delete itself worked. What came back was a *new* organization: `ensure_personal_organization()`
provisions whenever the caller has no `organization_members` row, and the app calls it from the
`_authenticated` guard on every navigation — so the redirect to `/dashboard` right after the delete
minted a replacement with the same generated name (`<email>'s Workspace`). The data really was
gone; it just looked untouched. The same mechanism undid Super Admin's `deleteTenant`: the tenant
reappeared as soon as its owner next signed in.

Fix (`supabase/migrations/20261105100000_deleting_an_organization_sticks.sql`): remember that a
user has already had their personal organization, and never auto-provision a second time.

- New `profiles.personal_org_provisioned_at`, set on first provision.
- Backfilled for everyone who already belongs to an organization. Without the backfill, an existing
  user deleting their only organization before their next provisioning call would still get a
  replacement — the exact bug being fixed.
- `ensure_personal_organization()` now returns NULL instead of provisioning when the marker is set
  and the user has no membership. It also sets the marker when it *finds* an existing
  organization, not only when it creates one, so the pre-migration population converges.
- New `create_organization_for_user()` for explicit creation, mirroring the provisioning body with
  a caller-supplied name. SECURITY DEFINER for the same reason as its sibling: the owner's first
  membership row cannot be inserted under RLS until the organization exists, and both must land
  together.

A user with no organization now lands on `/onboarding/organization`, a new route outside
`_authenticated` (that layout requires an organization). The `_authenticated` guard treats a null
`organizationId` as authoritative — it beats any cached selection, which would otherwise still
point at the deleted organization — and redirects there after clearing the tenant slots.

### Two smaller things found on the way

- `useDeleteOrganization` ran a client-side PostgREST delete under RLS. A DELETE matching no row
  succeeds with an empty result and no error, so a non-owner got "Organization deleted" for a
  delete that never happened. It now asks for the deleted ids back with `.select("id")` and raises
  a specific error when none come back.
- `pm_client_update_rules.created_by` references `auth.users` `ON DELETE RESTRICT` and was not
  cleared by `prepare_platform_user_deletion`, so account deletion would fail outright for anyone
  who had configured a client-update rule. (The table is empty in the live workspace, so this was
  latent, not the reported failure.) The prep function now deletes those rows. Audited the rest:
  of 159 `REFERENCES auth.users` across the migrations, every one declares an `ON DELETE` rule, and
  only three are RESTRICT — the two tenant-owner columns the prep function already handled, plus
  this one.

**Needs the user:** `supabase db push` to apply the migration. Until it runs, deleting an
organization still resurrects it.

## First-run setup was never reachable

On a fresh deployment against an empty database, nothing ever sent the operator to the setup
wizard. Both wizards existed — `/setup` (Environment → Administrator → Branding → System → SaaS →
Launch) and `/install` (the CodeCanyon one, with requirements and license steps) — but a search of
the codebase found **zero** navigations to either. The only mentions of those paths were in two
"skip tenant sync on these routes" lists. None of the three entry points (`/`, `/auth`,
`/_authenticated`) checked setup status, so a new install happily served its landing page, let
anyone sign up as an ordinary user, and rendered `/dashboard` — with no super admin in the
database and no way to discover that a wizard existed.

Everything else was already correct and was left alone: `getSetupStatus()` reads `user_roles` and
the `settings.setup_complete` flag; `bootstrapSuperAdmin` is gated on `SETUP_BOOTSTRAP_TOKEN` and
refuses once setup is complete or an admin exists; `.env.example` documents the variable. The gate
was the only missing piece.

**Added** `src/lib/setup/first-run-guard.ts` with two guards:

- `requireInstalledApp()` — on `/auth` and `/_authenticated`: if no super admin exists, redirect to
  `/setup`. Marketing, legal, docs, store, booking and embed routes are deliberately **not** gated,
  so a half-installed server still shows its public pages.
- `requireOpenInstaller()` — now the `beforeLoad` for both `/setup` and `/install`, replacing the
  copy-pasted guard each had.

**Scope decisions:**
- The gate asks "does a super admin exist", not "is `setup_complete` set". An admin is what makes
  the app usable, and installs that got one outside the wizard must not be herded back through it.
  This also means the live workspace (which has an admin but no `setup_complete` row) is unaffected.
- `/setup` is the forced destination; `/install` stays reachable on its own for license activation.
- A positive answer is cached per tab/process, so the check costs one request per page load and
  nothing per navigation. Negative answers are never cached, so the wizard releases the gate the
  moment it creates the admin.
- A failed status read is treated as "unknown" and lets the request through. Failing closed would
  throw every user of a live installation into the wizard over a transient database blip.

**Closed a re-entry hole in the wizards.** The old guard only locked them when `setup_complete` was
set — but an install can have a super admin and no flag, which is exactly the state of the live
workspace (verified: one `superadmin` row, zero `setup_complete` rows). A signed-in super admin
could therefore reopen `/setup` or `/install` and overwrite branding, localization, SMTP and SaaS
settings wholesale, or re-run the one-click installer. The wizards now open only for a genuinely
empty database, or for the session that is part-way through setting one up.

That exception is required, not cosmetic: `bootstrapSuperAdmin` is followed by
`signInWithPassword`, and the root route's `onAuthStateChange` calls `router.invalidate()` on
`SIGNED_IN` — which re-runs the wizard's own `beforeLoad` while the operator is on step 2 of 6.
`markWizardBootstrappedAdmin()` is called immediately before that sign-in so the guard recognises
the session as its own. The flag is in-memory on purpose: reloading the page re-locks the wizard,
which is the safe default.

Verified: ESLint clean on every file this change touched that uses LF endings
(`first-run-guard.ts`, `auth.tsx`, `_authenticated/route.tsx`, `__root.tsx`); `setup.tsx` and
`install.tsx` report only pre-existing CRLF/prettier noise, which is already in the working tree
and spans the whole file, not the edited lines. Full `tsc --noEmit` run after the change.

## Inbox: empty message bubbles (investigated — not an attachment bug)

Reported as "client attachments don't render". Checked against the live database: **every** inbound
media row has a `metadata.media_path`, the objects exist in the `attachments` bucket, and the
storage RLS policy (`attachments_select_workspace_member`, folder[1] = workspace id) matches the
path layout — so inbound media is ingesting and signing correctly.

The empty bubbles are a different defect. WhatsApp sends three message types the parser does not
know: `revoke` (sender deleted their message), `edit` (sender edited it) and `unsupported`
(e.g. an album). `mapMessageType` maps all three to `"unknown"`, which `processInboundMessage`
stores as `message_type: "text"` with `body: null` — and `MessageContent` renders nothing for that,
giving a bubble with only a timestamp. 15 such rows exist in the live workspace.

Not yet fixed — see the next session's notes.

## Inbox list: empty strip under short items, and the tick never turned blue

Two small list-item defects reported together.

unread badge was always rendered with `mt-1.5 min-h-[18px]`, so a plain thread (no label, nobody

- `supabase/migrations/20261105140000_conversation_last_message_status.sql` — new
  `conversations.last_message_status` column (`public.message_status`); `tg_message_after_insert`
  now writes it (the status for an outbound message, `NULL` for an inbound one); a new
  `trg_message_status_after_update` trigger carries a later receipt (`sent → delivered → read`) onto
  the conversation, guarded by a `NOT EXISTS` check that the message is still the newest in the
  thread — a timestamp comparison would not work because several senders overwrite
  `last_message_at` with their own clock after the insert. Backfilled from each conversation's
  newest non-internal message.
- `src/hooks/use-conversations.ts` — selects and types the new column.
- `src/components/app/inbox/conversation-list-item.tsx` — the tick is `text-sky-500` on `read`,
  muted otherwise, and a failed send shows a destructive `AlertCircle` instead. A `bot` reply counts
  as ours for this, same as `agent`.

`tsc --noEmit` is clean.

## Fresh database still showed the sign-in page instead of the setup wizard

Reported against a brand-new Supabase project (no migrations, no users): `/auth` rendered the
sign-in form even though the install has no super admin.

**Cause.** The first-run guard asks `getSetupStatus()`, whose first query is
`user_roles where role = 'superadmin'`. On a database with no schema that query does not answer
"no admin" — it *fails* (`PGRST205`, "Could not find the table 'public.user_roles' in the schema
cache"). `superAdminExists()` caught the error and returned `null`, which every caller reads as
"unknown, carry on" so a database blip never throws live users into the wizard. An uninstalled
database therefore took the same fail-open path as a healthy one. Verified the error shape against
a live project: `{"code":"PGRST205","message":"Could not find the table … in the schema cache"}`.

**Fix.**
- `src/lib/setup/setup.functions.ts` — `readSetupStatus()` now classifies the error. A missing
  relation (`42P01`, `PGRST205`, `PGRST202`, or a `does not exist` / `schema cache` message) is
  reported as `{ superAdminExists: false, setupComplete: false, databaseReady: false }` instead of
  throwing. Anything else still throws, so a genuine outage keeps the old fail-open behaviour and
  cannot open the wizard on a live install.
- `src/lib/setup/first-run-guard.ts` — `requireOpenInstaller` surfaces `databaseReady: false` as a
  step-1 message ("This database has no WACRM schema yet. Run the migrations…"), which also blocks
  `canProceed`, so the wizard explains the problem instead of failing on the create-admin button.
- `src/routes/auth.tsx` — the install check moved above the `typeof window === "undefined"` early
  return, so it runs during SSR as well. A fresh deployment now never paints the sign-in form; it
  redirects to `/setup` server-side rather than after hydration.

Note for the record: the service-role key in the local `.env` is rejected by the production project
(`401 Invalid API key`), so that check had to be done with the publishable key.

### Follow-up: the inbox must not depend on an unapplied migration

Selecting `last_message_status` before migration 20261105140000 is applied broke the whole list —
`column conversations.last_message_status does not exist`, so no conversations loaded at all.
`use-conversations.ts` now probes for the column once per tab (`hasLastMessageStatus()`) and leaves
it out of the select when the database does not have it; the type is optional and the tick simply
stays grey. The moment the migration is applied the probe sees the column and the blue tick starts
working with no further code change.

### Conversation-list menu: "Bulk select" was indented

`DropdownMenuCheckboxItem` reserves a left slot for its tick indicator (`menuItemClass("indicator")`
→ `pl-8`), so "Bulk select" sat one indent further right than "Manage labels", "Advanced search" and
the rest of the menu. It is a plain `DropdownMenuItem` now — same toggle behaviour, state shown by a
trailing `Check` instead of a leading one, so every icon in the menu lines up.

## First-run gate: whole router, and a wizard that names what the database is missing

Three related requirements, all for a freshly deployed server.

### 1. Everything except the marketing pages is closed until the app is installed

The gate was on `/auth` and `/_authenticated` only, so `/invite/:token`, `/reset-password`,
`/demo-login`, the storefront and every other route still rendered against an empty database. It is
now a `beforeLoad` on the **root route** (`src/routes/__root.tsx` → `guardAppEntry(pathname)`), so
anything added later is gated by default. Public while uninstalled: `/` (marketing landing),
`/setup`, `/install`, `/install-app`, `/docs`, `/legal`, `/privacy`, `/terms`, `/pricing`,
`/features`, `/about`, `/contact`, `/maintenance`, `/offline`, `/403`, `/api/*`, `sitemap.xml`,
`robots.txt`. Everything else redirects to `/setup`.

"Installed" still means **a super admin exists**, not `setup_complete`. This is deliberate and worth
recording: installs that created their admin outside the wizard never set that flag, and gating on
it would herd a live, working deployment into a wizard whose later steps overwrite branding,
localization, SMTP and SaaS settings wholesale. A database blip is likewise never treated as
"uninstalled" — only a missing schema is (see the previous section).

### 2. Setup cannot run twice

Unchanged but re-verified: `requireOpenInstaller` redirects `/setup` and `/install` to `/auth` when
`setup_complete` is set, and also when a super admin exists and the current tab is not the one that
just created it (`markWizardBootstrappedAdmin`). `completeSetup` writes the flag, so finishing the
wizard closes it permanently.

### 3. The wizard says which migrations and functions are missing

`validateEnvironment` used to check two tables and report the raw PostgREST message. It now reports
three probes, because the three failures have different fixes. The migration ledger
(`supabase_migrations.schema_migrations`) is not exposed over PostgREST, so readiness is measured by
asking for what the app actually needs:

- **Database migrations** — 12 core tables (`profiles`, `user_roles`, `settings`, `organizations`,
  `workspaces`, `workspace_members`, `inboxes`, `contacts`, `conversations`, `messages`,
  `channel_accounts`, `conversation_labels`). Lists the missing ones by name; `fail`.
- **SQL functions** — `is_super_admin`, `is_workspace_admin`, `is_active_workspace_member`, probed
  by calling them with a zero UUID. All three are read-only; nothing is written by the probe. `fail`
  when missing, with the schema-cache reload as the fix.
- **Schema is up to date** — columns from the newest migrations
  (`conversations.last_message_status`, `profiles.personal_org_provisioned_at`), which catch the
  install that looks healthy but stopped a few migrations short. `warn`.

Error codes verified against the live project rather than assumed:

| Condition | PostgREST answer |
| --- | --- |
| missing table | `PGRST205` "Could not find the table … in the schema cache" |
| missing column | `42703` "column conversations.last_message_status does not exist" |
| missing function | `PGRST202` "Could not find the function … in the schema cache" |
| function exists, no EXECUTE grant | `42501` "permission denied for function" — **not** reported as missing |

That last row is why the probe matches on the code rather than on "did it error": a permission
error means the function is there.

### The gate now asks "is setup finished", not "does an admin exist"

Previously an abandoned wizard left the app running on defaults forever: the admin existed after
step 2, so the gate opened and nothing ever brought the operator back to finish branding,
localization, SMTP or the SaaS settings. The gate now wants `setup_complete`.

The obvious danger is the reason it was not written that way to begin with — installations that
created their super admin outside the wizard never wrote that flag, and the stricter rule would
route those live deployments into a wizard whose later steps overwrite their settings with blanks.
Two independent protections, so neither a deploy order nor a forgotten migration can cause that:

- `supabase/migrations/20261105160000_setup_complete_backfill.sql` — writes
  `settings('platform','setup_complete') = {complete:true, backfilled:true}` **only** when a super
  admin already exists. A fresh database runs it before any admin exists, so nothing is written and
  the wizard still runs.
- `readSetupStatus()` derives the same answer at runtime, without writing anything, from the age of
  the oldest `superadmin` role: older than 24h ⇒ a pre-existing installation ⇒ complete. A wizard
  run in progress created its admin minutes ago, never a day. This makes the code safe to deploy
  **before** the migration is applied.

`/auth` keeps the looser rule (admin must exist, setup need not be complete), otherwise the wizard
— which asks the operator to sign in as the admin it just created — and `/auth` would bounce each
other forever.

**Verified** (not reasoned about — both run as scripts):

Migration, against PGlite with a stand-in `settings` + `user_roles` schema:

| Case | Result |
| --- | --- |
| fresh db, no admin | no row written |
| admin exists, no flag row | `{complete:true, backfilled:true}` |
| re-run | idempotent, unchanged |
| flag row said `complete:false`, admin exists | updated to `true` |
| flag row said `complete:false`, no admin | left alone |

`readSetupStatus`, with a stubbed admin client:

| Database | `databaseReady` / `superAdminExists` / `setupComplete` |
| --- | --- |
| empty (PGRST205) | false / false / false |
| schema, no admin | true / false / false |
| wizard mid-run, admin 2 min old | true / true / **false** |
| wizard finished, flag set | true / true / true |
| legacy install, admin 30 days old | true / true / **true** |
| admin 23 h old, no flag | true / true / false |

Routing, every state × every kind of path, by compiling `first-run-guard.ts` and stubbing its
imports:

| State | `/`, `/pricing`, `/docs/*`, `/setup` | `/auth`, `/reset-password` | `/dashboard`, `/inbox`, `/invite/*`, `/store/*` |
| --- | --- | --- | --- |
| no schema | allow | → `/setup` | → `/setup` |
| schema, no admin | allow | → `/setup` | → `/setup` |
| admin, setup unfinished | allow | allow | → `/setup` |
| setup complete | allow | allow | allow |
| database unreachable | allow | allow | allow (fail-open, by design) |

And `/setup` itself: opens on an empty database (with the "no schema" message) and on a database
with no admin; resumable by the tab that created the admin, or by a signed-in super admin in any
other tab; and permanently redirects to `/auth` once setup is complete — including in the tab that
ran it.

### Backfill in 20261105140000 failed on push (fixed)

`supabase db push` stopped at `20261105140000_conversation_last_message_status.sql` with
`42P10 invalid reference to FROM-clause entry for table "c"`. The backfill used a correlated
`LATERAL` subquery referencing the UPDATE's own target table, which Postgres does not allow in an
`UPDATE ... FROM`. Rewritten as a `DISTINCT ON (conversation_id)` CTE joined back to
`conversations`. The migration runs inside a transaction, so nothing from this file reached the
database; re-running the push picks it up from here.

Verified against PGlite this time, with the pre-existing `trg_message_after_insert` trigger in
place so the stub matches production:

| Step | Result |
| --- | --- |
| backfill, last message ours and read | `read` |
| backfill, last message theirs | `null` |
| backfill, newest row is an internal note | `delivered` — the note is skipped |
| backfill, conversation with no messages | `null` |
| new outbound message | `sent` |
| read receipt arrives | `read` |
| contact replies | `null` |
| late receipt on a now-older outbound message | ignored |
| whole migration re-run | idempotent |

## Existing customers stranded with no super administrator

Buyers of earlier builds installed the app, ran it, and then could not find or create a super
administrator. Two things made it impossible, both fixed:

1. **`bootstrapSuperAdmin` refused without `SETUP_BOOTSTRAP_TOKEN`.** The wizard's "Create Super
   Administrator" step returned "Set SETUP_BOOTSTRAP_TOKEN … on the server" and there was no way
   forward for anyone who had not set that variable before installing. The token is now **optional**:
   required when the operator has set it, skipped when they have not. Everything else that guards
   this endpoint is unchanged and still enforced — it works only while `setup_complete` is unset AND
   no `superadmin` exists anywhere, so it can be used exactly once, to recover an installation that
   has nobody in charge of it.
2. **The owner's email usually already had an account**, so `createUser` failed with "already
   registered" and the step dead-ended. The handler now looks the address up first and **promotes
   the existing account** instead. Its password is deliberately *not* changed — the account belongs
   to a real person and this endpoint is unauthenticated — and the response says so
   (`promoted: true`), so the wizard skips its automatic sign-in rather than reporting a failure.
   A role-insert failure now only rolls back an account this call created, never a pre-existing one.

### `supabase/patches/recover-super-admin.sql`

For installations that cannot even reach the wizard, a standalone patch to paste into the Supabase
SQL Editor. Edit two values at the top, run, read the notices. It is idempotent and refuses to run
with the placeholder email still in place. Verified against PGlite with a stand-in `auth` schema:

| Scenario | Result |
| --- | --- |
| no admin, new email | account created, confirmed, `auth.identities` row written, role granted |
| no admin, email already exists | that account promoted — password hash untouched (`KEEPME`) |
| a super admin already exists | nothing changed, notice says so |
| placeholder email left unedited | refuses with a clear exception |

## Voice notes did not work in Chrome, and dictation did not exist

### Why recording failed

`MediaRecorder` in Chromium cannot produce Ogg. The composer asked for
`audio/ogg;codecs=opus` → `audio/ogg` → `audio/mp4`, none of which Chrome supports, so it fell back
to WebM. `channel-attachments.ts` lists WhatsApp's accepted audio types as aac/amr/mpeg/mp3/mp4/ogg
— **not** webm. So every recording made in Chrome or Edge was checked *after* the user finished
speaking, rejected with "Voice note not supported here", and thrown away. On Safari it worked,
which is why it looked intermittent.

Fixed by repackaging rather than refusing: `src/lib/media/webm-opus-to-ogg.ts` lifts the Opus
packets out of the WebM (Matroska/EBML) container and writes them into Ogg pages with the
OpusHead/OpusTags headers RFC 7845 requires. No re-encoding — the audio inside a Chromium recording
is already Opus, which is exactly what Ogg/Opus wants; only the wrapper changes. If the input turns
out not to be WebM/Opus the function returns `null` and the original file is used.

Verified by building a synthetic WebM with 120 known Opus packets across two clusters and checking
the output (13 assertions, all passing):

| Check | Result |
| --- | --- |
| every packet found, in order | 120 / 120 |
| packet length read from the TOC byte | 960 samples (20 ms) |
| output MIME | `audio/ogg`, 1974 bytes |
| duration | 2400 ms, as recorded |
| every Ogg page checksum | valid (5 pages) |
| page sequence numbers | 0..n, no gaps |
| first two pages | `OpusHead`, `OpusTags` |
| final granule position | 115200 = 120 × 960 |
| end-of-stream flag | set on the last page |
| audio payload after the round trip | byte-identical, 120 packets |
| non-Opus input / empty input | refused, so the caller falls back |

### The other recording defects, also fixed

- **The microphone stayed live** after switching conversation or navigating away — nothing stopped
  the `MediaStream` tracks, so the browser's recording indicator kept burning. Now released on
  unmount, on cancel, on error and on stop.
- **A 0-byte voice note** could be produced by stopping immediately: `rec.start()` had no timeslice,
  so the single final chunk could be empty. Now `rec.start(1000)`, plus an explicit empty check with
  a message instead of a silent broken attachment.
- **No way to cancel.** Starting a recording committed you to attaching it. There is a discard
  button now.
- **No feedback.** Added a live `m:ss` timer with a pulsing dot, and an automatic stop at 5 minutes
  so a forgotten recording cannot run all day.
- **"Microphone access denied" for every failure**, including having no microphone at all. The two
  cases are now reported separately, each with the fix.
- `MediaRecorder` missing entirely is detected up front instead of throwing.

### Dictation (speech → text)

New button in the composer toolbar, beside the emoji picker: it types what you say into the message
box, as opposed to the microphone on the right which records audio to send. Web Speech API,
continuous, with interim results shown live and replaced as the engine settles them, appended to
whatever was already typed. Uses the browser's own language (`navigator.language`). Where the API is
missing the button explains that and points at the voice note instead; `no-speech` and `aborted`
end quietly rather than raising an error toast.

## `supabase db push` kept failing with ECONNREFUSED 127.0.0.1:54322

**Cause, not a bug in this repo:** Supabase CLI v3 (3.0.0 is installed here) changed `db push` to
target the **local** stack by default. `npx supabase db push` therefore tries to reach a local
Postgres on `127.0.0.1:54322`, finds no Docker, and dies — every time. The remote now has to be
asked for explicitly: `--remote`.

A second, quieter problem sat behind it: `--remote` alone pushes to whatever the CLI happens to be
linked to. The link pointed at **wpscrm** (`zoafvyuybkkfkypkqwgq`, a customer project) while `.env`
and `supabase/config.toml` both point at `qtlspjkuhfyyesgtkpcv` (WRAPCODERS.BID). A plain
`--remote` push would have applied this repo's migrations to a customer's database.

**Fix — `scripts/db-push.mjs` (new), wired to `npm run db:push`:**
- resolves the target project from `.env.local`/`.env` (`SUPABASE_URL`, else `VITE_SUPABASE_URL`),
  which is the project the running app actually talks to;
- refuses to run when the CLI link disagrees with that, printing both refs and the exact command to
  fix the link — `--ref=<project-ref>` overrides when another target is intended;
- pushes with an explicit `--remote=<ref> --include-all --yes`, so nothing is left to the CLI's
  default.

New scripts: `npm run db:push`, `npm run db:push:dry`.

**Verified:** the guard fired on the real mismatch; after `npx supabase link --project-ref
qtlspjkuhfyyesgtkpcv` the dry run connects to WRAPCODERS.BID and lists the two still-pending
migrations (`20261105140000_conversation_last_message_status`,
`20261105160000_setup_complete_backfill`; `20261105100000` is already applied). The real push is
blocked for this session by the production-deploy guard and has to be run by hand.

Also corrected `package.json`, whose version field had become `"v7.2.3"` — not valid semver, and
npm printed it back as `wacrm@v7.2.3`.

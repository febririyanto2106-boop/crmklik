## 2026-10-31 — Chat widget: size memory, transparent frame, and corner-aware motion

Four fixes to the embedded live chat widget (`src/routes/embed.w.$widgetId.tsx`, plus the loader at `src/routes/api/public/widget/embed.ts`).

1. **Reopening always jumped to full screen.** The minimized launcher's click handler was hardcoded to `changeWindowState("maximized")`, so collapsing the panel to its docked size was forgotten the moment you minimized or closed. Added a second persisted key, `wacrm.widget.size.<widgetId>` (`"open" | "maximized"`), written on every non-minimized state change; the launcher now reopens at `readWindowSize(widgetId)`. Minimizing no longer erases the size to come back to, and the first-ever open is the docked widget rather than full screen.
2. **White card around the launcher on the host site.** The loader's iframe is already `background:transparent`, but the app's global `body { background-color: var(--color-background) }` painted the page white, which showed through the loader's frame as a white box (very visible over a dark section — see wrapcoders.com). The embed route now clears `html`/`body` backgrounds on mount and restores them on unmount.
   - **Clearing the backgrounds turned out not to be enough.** The root theme bootstrap (`THEME_BOOTSTRAP_SCRIPT` in `src/routes/__root.tsx`) sets `document.documentElement.style.colorScheme` to the resolved `light`/`dark`. With a resolved colour scheme the browser paints an **opaque UA canvas** behind the iframe, which `background: transparent` cannot clear — so the white panel persisted. Fixed by also setting `color-scheme: normal` on `<html>` for this route, and writing the backgrounds with `setProperty(…, "important")` so no stylesheet rule can win them back. Both are restored on unmount.
3. **Motion was generic and came from the wrong direction.** The panel animated `translate-y` only, regardless of which corner the launcher sits in. It now reads `config.launcherPosition` (already returned whole by `/api/public/widget/config/:widgetId`) and derives the corner: anchor classes, a matching `origin-*` transform origin, and a collapsed transform that translates toward that corner. So a left-mounted widget grows from the left, a right-mounted one from the right. Easing moved to `cubic-bezier(.16,1,.3,1)` at 420ms for both the panel and the launcher button, and the **loader's** iframe resize transition was changed to the same `.42s cubic-bezier(.16,1,.3,1)` so the outer frame and inner panel move as one instead of fighting each other. `motion-reduce` and the loader's `prefers-reduced-motion` branch are both preserved.
4. **Maximized view stranded the bubbles at opposite window edges.** `isMaximized` only swapped button icons; the transcript, quick replies and composer stayed full-bleed across a ~1500px window. They now share a centered `max-w-3xl` column in maximized mode only (`src/components/app/widget/live-chat-widget.tsx`), leaving the docked size untouched.

## 2026-10-31 — Live chat answered with no grounding whenever embeddings were unavailable

- **Bug**: `retrieveKb()` in `src/lib/widget/livechat-ai.server.ts` wrapped the whole vector lookup in `try { … } catch { return [] }`. Any embedding failure — provider outage, exhausted quota, billing lapse — therefore returned *zero* knowledge-base hits, silently. The reply pipeline treats an empty result as "nothing relevant in the KB", so the bot kept answering confidently from model weights alone, with none of the workspace's facts. A grounded assistant quietly degrading into an ungrounded one is worse than an outright error, because nothing in the UI or the logs says it happened.
- **Found while** seeding a knowledge base: the embedding endpoint returned `402 … prepayment credits are depleted`, and the bot carried on answering as if nothing was wrong.
- **Fix**: added `keywordKbFallback()` — when the vector path throws *or* returns no rows, it runs an `ilike` search over published `kb_articles` for the workspace and feeds those to the model instead.
  - Visitor text reaches a PostgREST filter string, so every term goes through `ilikePattern()` from `src/lib/api/postgrest-filters.ts` before interpolation. Terms are capped at 6 and words of 3 characters or fewer are dropped.
  - **Ranking matters here.** The first cut used `.or(…).limit(n)`, which returns whichever rows Postgres reaches first — one common word ("what", "need") was enough to hand the model a pile of irrelevant articles, and it then filled the gaps itself (it invented a hosting provider that appears nowhere in the KB). Now it over-fetches 40 candidates and scores them in JS — title match 5, summary 3, body 1 — then takes the top `matchCount`. Snippets widened from 400 to 1200 characters, since a whole article truncated at 400 cuts off before the facts.
- **Verified** end to end through the real widget endpoints (`/api/public/widget/session` → `/api/public/widget/chat`) with embeddings still failing: server requirements, product + price, an unsupported-feature question, and an escalation request all answered correctly from the KB, with no invented specifics, and the refund request set `handoff: true`.
- **Related data fix**: the live chat bot was still pinned to the retired `google/gemini-2.5-flash` (see the model sweep above). Its `model` is now resolved from the workspace's own enabled `ai_providers`/`ai_models` rather than a hardcoded string.
- **Environment issue, not a code bug** (needs the account owner): the `GEMINI_API_KEY` used for embeddings returns `402 RESOURCE_EXHAUSTED`. Vector indexing cannot run until that account has credit; the keyword fallback above is what keeps the KB usable meanwhile. Chat completions are unaffected because they use the workspace's own BYOK provider key, not this one.

## 2026-10-31 — Live Chat automations were enqueued but never ran

- **Bug**: `wf_queue_lease` (migration `20260717160746…`) only leases rows whose `status = 'queued'` (or a `'running'` row whose lease expired), and the `workflow_queue` table defaults `status` to `'queued'`. But three enqueuers inserted `status: 'pending'`, a value nothing ever leases. Those jobs sat in the queue forever: the automation showed as **active**, the row showed as **pending**, and no error was raised anywhere — the only visible symptom was `runs_count` never leaving 0.
- **Reproduced**: created three Live Chat automations, fired real `/api/public/widget/track` events, confirmed rows landed in `workflow_queue`, then ran the worker — `{"processed":0}` against two ready jobs.
- **Fixed** (`'pending'` → `'queued'`):
  - `src/lib/livechat/livechat-automation.server.ts` — the widget's dispatcher. This is the path every Live Chat automation takes, so **no Live Chat automation on this install had ever executed**.
  - `src/lib/livechat/automation-actions.server.ts` — the "run workflow" action available to Live Chat flows.
- **Verified** end to end after the fix: tracked pageview → row enqueued as `queued` → `/api/public/hooks/workflow-queue` leased it → `{"processed":1,"status":"success"}` → `runs_count` 1 → 2 with `last_run_status: success`. Rows already stuck as `pending` were released to `queued` and also ran successfully.
- **Related, NOT fixed — needs a decision**: `src/lib/helpdesk/sla-engine.functions.ts` (~line 445) inserts into `workflow_queue` with `trigger_type` / `trigger_data`, columns that do not exist on that table (it has `trigger_source` / `input`), and omits `automation_id`, which is `NOT NULL`. That insert can never succeed, and it is wrapped in `.then(() => {}, () => {})` so the error is swallowed silently. Making it work needs a decision on how an SLA `workflow_event` string maps to an `automation_id` — so it was left alone rather than guessed at.

## 2026-10-31 — SLA escalations now reach the workflow engine

- **Bug** (the item left undecided in "Live Chat automations were enqueued but never ran"): the SLA → workflow bridge in `src/lib/helpdesk/sla-engine.functions.ts` inserted into `workflow_queue` with `trigger_type` / `trigger_data` — columns that table does not have (it has `trigger_source` / `input`) — omitted `automation_id`, which is `NOT NULL`, and used `status: 'pending'`, which `wf_queue_lease` never leases. The insert was wrapped in `.then(() => {}, () => {})`, so every failure was swallowed: an escalation rule with a **Workflow event name** set looked configured and did nothing, with no error anywhere.
- **The decision it needed** was how a free-text `workflow_event` maps to an `automation_id`. Resolved by following the convention the engine already uses for every other event (`emitWorkflowEvent` in `src/lib/workflows/workflows.functions.ts`): the event name is matched against `automations.trigger_type`, and one queue row is enqueued per subscribed automation.
- **Fix**: new exported `enqueueSlaWorkflowEvent()` in the same file. It resolves subscribers two ways, so an existing install keeps working and a new flow is easy to build:
  1. `automations.trigger_type` equals the event name verbatim (the `emitWorkflowEvent` convention).
  2. The automation starts with the new **SLA escalated** trigger node, `trigger.helpdesk.sla_escalated` (added to `src/lib/workflows/node-registry.ts`, category *Helpdesk*). Its optional `event` field narrows the subscription to one event name; left empty it catches every SLA escalation.
  Each row is written with the real schema — `automation_id`, `version`, `trigger_source: "sla"`, `event_type`, `input` (event, ticket, level, escalation rule, policy) — and `status: "queued"` so the worker actually leases it. An `idempotency_key` of `sla:<rule>:<ticket>:<level>` makes a repeated scan a no-op against `workflow_queue_idem_uidx` instead of a duplicate run, and a `23505` conflict is treated as that benign replay. Lookup failures are logged, never thrown: a broken workflow must not abort the breach scan.
- The escalation-rule dialog (`src/routes/_authenticated/helpdesk.sla-management.tsx`) now explains under the field which workflows the name will run, since a silent no-match was the original failure mode.
- **Verified**: new `tests/unit/sla-workflow-bridge.test.ts` — 7 tests covering the leasable row shape (`status: 'queued'`, real `automation_id`, no `trigger_type`/`trigger_data`), the two-way subscriber lookup, an event-name filter that must not match, fan-out to multiple subscribers, the no-subscriber and blank-name no-ops, and the duplicate-key replay.
